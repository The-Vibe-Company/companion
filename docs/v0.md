# V0 implementation status

> Scope update, 11 September 2026: [Discussions and companions](specs/discussions.md)
> supersedes the specialist, routine, trigger and single-chat model below. Permanent companion
> machines, connections and memory remain; each discussion now has an independent Pi history.

This document describes what the repository implements on 7 September 2026 and where it still
falls short of the approved product in [companions-build.md](companions-build.md). It is an
implementation boundary, not a launch declaration.

Specialists now have conversational configuration drafts, selected MCP accounts, prepared-disk
publication, an optional test mission, per-team connection overrides, an initialization journal,
improvement proposals and account/provider admission limits. The executable contract and lifecycle
are described in [lifecycle.md](lifecycle.md) and [UI_CONTRACT.md](UI_CONTRACT.md); the design is in
[the specialist specification](specs/specialists-configuration-and-lifecycle.md). Prepared specialist
delivery is an explicit disk-copy choice and requires recipient MCP reconnection. Earlier notes
below about profile-only specialist delivery describe the legacy path.

Opaque improvements use assisted reconstruction in the draft; no general disk merge is claimed.
Public preview relay remains deferred. Local behavior tests and Docker image tests cover this
implementation; the new end-to-end Box onboarding flow still requires a live provider canary.

## Architecture and authority

PostgreSQL is the web source of truth. Better Auth stores personal users and sessions in the same
database. Product rows carry the immutable Better Auth user ID, and authenticated queries scope
reads and writes to that owner. There is no hosted operator-token bypass. Local sign-in also uses
the real magic-link flow through an isolated Mailpit instance.

The API validates authorization and commits messages, files, lifecycle requests, webhook receipts,
and configuration. It does not contact Pi for ordinary admission. The executor holds the database
lease and is the sole owner of machine and Pi effects. The worker schedules routines, evaluates
trigger deliveries, and flushes usage without contacting a Companion directly.

Each Companion has a durable main lane and background lane. Main messages use Pi's native steer
behavior against one persistent chat session. Routines, triggers, and delegated tasks use distinct
background sessions. The control plane records dispatch intent before contacting the daemon; the
daemon journals request IDs beside Pi history. An ambiguous effect is interrupted and is not
blindly replayed.

## Implemented product behavior

### Accounts, chat, files, and machines

- Email magic-link sign-in, sign-out, 30-day sessions, hashed one-time tokens, and cross-account
  ownership tests use Better Auth and PostgreSQL.
- Companion identity includes name, mission, expressive shape/color/face avatar, and a validated
  model selected from configured providers.
- Message admission returns `202` after persistence. Stable client IDs deduplicate retries and
  reject changed content. A same-origin event stream signals committed chat changes and the UI then
  reloads the owner-scoped PostgreSQL snapshot and reconciles loaded chat pages; partial Pi text appears only while the corresponding
  main run is active. Notifications are deliberately not a durable log: reconnect always refreshes
  the recent snapshot and loaded intervals, so a notification missed while offline cannot lose persisted state.
- Typing `/` in the chat composer discovers the current runtime's Pi skill commands. Selection
  inserts `/skill:<name>` at the caret without sending; Pi alone expands leading skill commands.
  Mid-message and unknown commands retain their submitted content. Discovery exposes only names,
  descriptions and source scope/origin, respects Pi's command setting, and never wakes a sleeping
  Companion. Unavailable or older runtimes leave ordinary message submission available.
- Up to five validated private images or documents can be attached to a message. Dispatch waits
  for every declared upload. Agent outbox files are copied to private object storage and projected
  onto the corresponding message or retained delegated task. Parent reviews receive owner-scoped
  references atomically with their queued run; the executor stages verified bytes even after the
  child Box is archived, and Activity exposes the retained download.
- Local machines run the compiled Pi/Bun distribution in isolated Docker Linux. Box machines are
  created from a prepared snapshot and resume their existing disk. No runtime package install is
  performed during wake.
- Provider observation records externally archived Boxes as `archived`, closes the corresponding
  usage interval once, clears stale endpoints, and presents the durable disk as “Sleeping” in the
  web client.
- Cancellation, task-scoped questions, durable answers, restart reconciliation, and terminal task
  results are integrated. A suspended background task releases its lane and resumes from its
  persisted answer.
- Main and background Pi sessions share Companion-local structured memory while retaining separate
  native Pi histories. A bounded preference/correction snapshot is available immediately; detailed
  retrieval, indexing and maintenance use a lazy subprocess. Legacy `MEMORY.md` and its atomic
  versioned tools remain supported. Templates inherit only explicitly reusable setup/procedures
  through product memory. See [fast-start memory](fast-start-memory.md) for isolation, failure
  behavior, compatibility and verification. Generic file and shell access remains an instructed-against
  same-user bypass, not a hard filesystem boundary.

### Collaborative conversation

- Open-ended wishes start with one or two concrete questions before the Companion chooses a
  workflow, installs skills or changes its mission. Specific tasks and agreed steps proceed
  within their authorized scope. Blocking decisions use the persisted `ask_user` question.
- Visible assistant messages, including partial text, are journaled per response root with stable
  sequence numbers and projected into PostgreSQL. Polling and restart reconciliation preserve
  them without duplicating the final answer. Thinking and tool payloads remain separate.
- Questions show an explicit waiting state, suggested answers and free text. Answered and closed
  questions stay in history; closed questions no longer imply that the Companion needs input.
- Existing runtimes without message snapshots retain the legacy final-answer path. Earlier
  intermediate messages that were never persisted cannot be reconstructed by this change.

### Automations, plugins, and control

- Routines support CRUD, IANA time zones, five-field cron schedules, deterministic occurrence IDs,
  history, and last-occurrence catch-up with persisted missed windows.
- Routine publication modes are `auto` (default, explicit `publish_to_chat`), `always`
  (publish the successful result), and `silent` (suppress result messages, retain questions).
  Manual and scheduled admission snapshot routine identity, name and mode on the run; edits
  affect only future admissions. Chat shows persisted execution markers, groups consecutive
  silent successes, and replaces a marker with its attributed published message. Execution
  details load on demand in a side panel. Legacy manual tests have no recoverable routine
  identity; older scheduled names are backfilled from the retained routine.
- Triggers are Composio trigger subscriptions per Companion: signed webhook verification, delivery
  deduplication, encrypted payloads staged as workspace files, and one background task per delivery.
  See [production apps and triggers](plugins-production.md).
- Apps are Composio toolkits connected through Composio-hosted consent and owner-scoped; custom
  HTTPS and stdio MCP definitions are supported, and native GitHub OAuth provides git access only.
  Access is selected per Companion; Composio tools execute on the executor, which alone holds the
  Composio key.
  MCP calls execute directly without per-call human approval, including tools marked destructive
  or lacking annotations.
  Older agent runtimes receive an automatic acknowledgement for their retired approval operation;
  existing unanswered approval questions resolve in place without replaying calls or overriding
  explicit answers or unknown outcomes.
- The compiled agent receives a `companion-control` MCP. It can inspect and change identity/model,
  routines, triggers, selected plugins, tasks, questions, delegation, replicas, templates,
  lifecycle intent, connections, and delivery preparation through durable command IDs.
- The `history_search` control operation uses indexed full-text search over this Companion’s completed prompts and results. It returns at most ten bounded excerpts, excludes the current task and other Companions, and never indexes staged instructions.
- Background work remains visible in activity and can explicitly call `publish_to_chat`. The daemon
  journals that choice and the executor publishes the settled text into the main conversation in
  the same durable settlement path.
- The web sheets expose routine test/history and missed windows plus provider account/target setup,
  declared trigger reads, code filtering, test evaluation, delivery decisions, and registration
  recovery. Advanced controls stay collapsed until requested.

### Templates, replicas, desktop, billing, and delivery

- Permanent Companions can authorize a template with a bounded child count, start temporary
  specialists, delegate to another permanent Companion, receive retained results, and prevent
  recursive child creation.
- A completed Box child can become the next snapshot for a template. Snapshot intent and its
  unique name are durable before provider contact; an uncertain capture is observed rather than
  submitted again. Temporary children archive only after outputs and any selected snapshot are
  durable.
- Template changes append immutable revision rows. Owner-scoped history and optimistic rollback
  restore a prior profile, snapshot, and portable-skill bundle as a new revision. The web exposes a
  compact revision selector and Restore action; the control MCP exposes the same operations.
- Opening a Box desktop requests preparation when needed. Takeover and release are durable intents.
  The UI retains the tab opened by the user's click while desktop preparation is pending and does
  not claim human control until the executor records the confirmed pause.
- Stripe billing has hosted Checkout, customer portal, raw signed webhooks with durable event
  deduplication, subscription state, and an owner-scoped usage ledger for model tokens and Box time.
  Missing hosted configuration returns an unavailable state rather than a fake plan. Explicit
  local test mode permits deterministic activation without a live charge.
- A sender can invite a verified email to activate a fresh, independently owned Companion. The
  delivery copies name, instructions, avatar, selected declarative specialist profiles, and bounded
  local Pi-skill packages through immutable private bundles.
  It excludes snapshots, histories, connections, OAuth tokens, browser sessions, and machine
  credentials. Maintenance must be requested, explicitly accepted, and can be revoked.
- Delivery creation persists a client intent ID and request fingerprint, making unchanged retries
  idempotent and rejecting reuse with different delivery details. Hosted Companion creation,
  and delivery activation require the configured subscription entitlement; development test
  activation remains explicit. Delivery stays unavailable while skill export is pending or failed;
  the form and Account list show `skillsStatus` rather than claiming an email was sent.
- An accepted maintenance grant exposes only bounded status/configuration, preparation, background
  maintenance tasks, and an action history. The UI states this scope; chat and files are excluded.
  Revocation prevents further access and cancels queued or requests cancellation of active work.
- Work-starting API and control-MCP mutations recheck hosted activation. The executor also rechecks
  immediately before new machine/model work, while terminal harvesting, cleanup, and cancellation
  remain possible after revocation.
- Portable Pi-skill manifests have bounded export/import, content hashes, unsafe-path and
  credential-file rejection, immutable private bundles, delivery readiness, and lifecycle staging
  for the delivered Companion and its selected specialist replicas. Snapshot adoption binds the
  captured bundle to the immutable template revision, and re-entry skips an already staged hash.

## Validation status

`python3 scripts/verify.py` provisions fresh PostgreSQL and MinIO, installs from frozen lockfiles,
typechecks, builds the agent, runs server and real compiled Pi/Linux behavior suites, then tests and
builds the web client. It labels and removes only containers owned by that verification run.

The deterministic suites cover ownership isolation, durable admission, event-stream reconnect and
snapshot recovery, crash boundaries, native steering, independent lanes, questions, routine
catch-up, signed triggers and filters, files,
plugins, lifecycle state, template adoption, billing signatures and usage deduplication, delivery
isolation, and the local end-to-end product path. The wider experiment covers packaging resources,
skills, MCP HTTP/stdio, image input, session continuity, cancellation, and faults. See
[testing.md](testing.md) for exact evidence boundaries.

Targeted live canaries have exercised one real model and Box snapshot/create/tool/archive/resume
paths. A portable-skill canary verified hashed export, idempotent import, daemon discovery, and
actual Pi use on the V3 snapshot, with the PostgreSQL result matching the daemon journal. V5
canaries verified retained delegated-file handoff plus native memory/history use. A separate
desktop canary froze a real 25-second shell subprocess for 28 seconds during
takeover, resumed it, and observed successful completion; VNC was also used to open a terminal.
Those checks are credentialed individual observations, not the normal development loop. The latest
Box cold and wake paths still take tens of seconds. No current evidence establishes hosted load,
tail latency, continuous reliability, or the desired few-second cold startup.

The runtime review findings are fixed: independent run jobs keep slow network observations out of
the admission loop, and captured-leader guards reject late effects and checkpoints. Twelve focused
fault tests cover these boundaries, including delayed PUTs, stale health replies, lost leadership,
revoked authority, and concurrent migrations. Final product-core verification `bcdfc7fd8178`
passes with the account, template, history, handoff, and shared-memory fixes integrated.

Manual routine tests use the same transactional admission through the API and control MCP.
A disabled routine can be tested without enabling or rescheduling it. Editing its name, prompt or
calendar also preserves its enabled state unless the update explicitly changes that state. Deletion locks the same
routine row as manual admission: once deletion commits, the old identifier cannot create new work.
Routine creation, scheduled admission and background admission reject companions whose retirement
has been requested or completed; idle archival remains compatible with normal scheduled wake-up.

Webhook admission and its batch link commit atomically. Grouping locks the actual task state, and
reclaimed evaluations reject stale worker decisions. A task awaiting human input can coexist with
its active successor without violating the trigger projection. Disabled or retiring automations
are rechecked before admitting new work. The integrated PostgreSQL 18 suite and hosted source,
migration and unauthenticated-access checks are recorded in
[the automation stability measurement](measurements/automation-stability-2026-09-07.json).


### Team setup and early preparation

The guided team flow requests `prepare:true` for a new coordinator, so the executor can prepare
its computer while permissions are saved and the user composes a message. Adding specialist
profiles to an existing coordinator only updates permissions; it neither wakes the coordinator
nor spawns replicas. Team remains a view of a coordinator's permissions, not a new runtime
or tenant entity.

The companion creation API still accepts explicit `prepare:false` for intentional lazy callers.
Omitting it defaults to true. This value participates in the durable creation fingerprint:
retries must preserve it. Older browser setup requests are replayed unchanged, then request
preparation through the durable lifecycle endpoint after creation acknowledgement.

### Removing a Companion

The owner can `DELETE /api/companions/:id`; the API returns `202` with
`{deleted:true,companionIds:[...]}`. Repeating the request returns the same owned identities.
Removal hides the Companion and its owned temporary children immediately, disables routines and
triggers, rejects new chat/preparation, and requests cancellation in both lanes. An outgoing task
on a permanent Companion is cancelled without removing that target. Connections, saved profiles,
accepted client copies, retained files and chat history are preserved. Direct owner reads remain
available for history; removal is not a hard purge.

The executor continues processing retirement intents after `retired_at` is set. It can cancel
existing Pi runs using the private endpoint, then archives the existing computer and observes
confirmation before completing remaining run cancellations and recording usage. It neither wakes
nor replaces a computer to remove it. A successful Docker lookup reporting no owned-name container
completes local cleanup; an unavailable Docker transport does not.

Previously submitted template captures are observed by name, never posted again. Removal waits
for confirmed ready/failed capture status and preserves the previous saved template. After ten
minutes without confirmation it exposes a reconciliation error and retains the source computer;
a missing response alone does not prove the capture had no effect. Similarly, an ambiguous Box
creation without its original ID requires reconciliation rather than creating a replacement.

## September 7 stability follow-up

Retirement and delegation-review admission now share the owner graph lock and parent/child lock
order, so a returned review cannot outlive deletion as newly queued work. Manual routine tests
lock the Companion before the routine, matching retirement. Lifecycle selection rotates before
its bounded candidate limit, preserving four concurrent jobs while allowing new preparation past
100 unresolved cleanup intents. PostgreSQL regression tests reproduce the original failures.

The web preserves message and upload identities only for the same ordered metadata and SHA-256
attachment contents. An unresolved upload must be retried unchanged or explicitly cancelled before
replacement; a failed cancellation keeps its identity. This prevents creating another command that
would wait behind an incomplete upload. These changes do not automatically replay ambiguous work.

Settings retain drafts across main tabs and guard exits to other Companions/pages, including
browser history. Saves PATCH only edited fields, preserving untouched agent changes and whitespace.
Applications selection is serialized, reloaded from the server after success or failure, and errors
are visible. Applications retain direct access in the flat companion navigation.

## Activity and live Team projections

Activity lists tasks through owner-scoped cursor pagination (20 by default, maximum 50). Opening
a task reads its original request, result, persisted state and files without requesting every
task's body. The cursor retains PostgreSQL microsecond ordering and the UUID tie-breaker.
Background tasks can be cancelled independently. A dispatched main turn may share a native Pi
response with other steers, so its isolated cancellation is rejected; the discussion retains the
explicit stop action for the shared reply. Retirement preserves task reads and disables mutation.

Template and permission commits send identifier-only invalidation hints to the affected owner's
Companions. An open Team reloads its projections with coalescing, preserves drafts and mutation
errors, and ignores stale responses. The app also ignores responses for Companions left behind.
This work does not yet paginate the durable chat snapshot; that separate audit item remains open.

## Reference design (September 7)

The web follows the owner-provided Claude design direction: ivory canvas, a 96px companion rail,
sticker avatars, pill navigation, aligned chat rows, account tiles, compact Settings and a split
creation page. Applications remain a direct companion section and also appear in Settings.
`/specialists` manages existing reusable profiles and their revisions; template access still comes
from the calling companion. The design contract is in `docs/design-system.md`.

New creation selects existing accounts and specialist permissions before opening the chat. It
persists a `prepare:true` companion and resumes additive grants using the same creation identity;
a failed optional grant can be completed later from the created companion. Preparation is
requested before these grants, without a model warmup request. An owner-scoped session journal
survives reload, including the acknowledgement of preparation for older lazy requests. Internal
navigation is held during unresolved setup, and detached async responses cannot navigate the
user. Opening the creation form alone does not start a computer.
